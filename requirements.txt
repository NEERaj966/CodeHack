# Campus Resource Intelligence - Project Requirements

## Overview
This project implements a campus resource-sharing platform for college-owned equipment, labs, classrooms, and facilities. The system is built from the SRS v1.1 document and focuses on a single-college prototype with strong governance and traceability.

## Core product requirements

### Functional requirements summary
- User registration with college email verification
- Role-based access for student, resource manager, department owner, and administrator
- Resource inventory management by authorized staff
- Search and discovery for campus resources
- Eligibility checks, training verification, and supervisor approval rules
- Booking request workflow with approval, rejection, cancellation, extension, and waitlist
- FairShare allocation with active-booking/category limits, weekly-hour limits, cooldown, and explanation text
- QR/token-based pickup and return
- Condition reporting at pickup and return with dual acknowledgment
- Incident, maintenance, penalty, and appeal handling
- In-app notifications and reminder scheduling
- Resource utilization analytics and demand intelligence
- Append-only audit logging

### Priority focus
- P0 (implemented in the app): college-domain student registration/email verification, role enforcement, inventory/discovery, eligibility checks, bookings/decisions/waitlist, FairShare limits, conflict protection, pickup/return condition records, incident reporting, notifications/overdue escalation, and append-only audit history
- P1 (deferred): teams, training document review/expiry, cancellation/extensions, no-show and maintenance conflict flows, appeals/penalties, and waitlist claim windows
- P2 (optional/stretch): AI matching, advanced analytics, CSV export, fee integration

## Non-functional requirements summary
- API responses for standard operations must complete within 2 seconds under prototype load
- Production must use HTTPS
- Passwords must be hashed securely with bcrypt or argon2
- Authorization must be enforced by the backend for every sensitive operation
- Input validation must defend against injection, XSS, and CSRF issues
- Uploads must be validated for type, size, and access rights
- Image/evidence storage must use authenticated or signed URLs
- Audit log must be append-only
- Booking conflict prevention must work under concurrent requests
- UI must be responsive and accessible (WCAG 2.1 AA target)
- Secrets/configuration must use environment variables
- Privacy rules must protect personal and evidence data

## Technology stack
- Frontend: React + Vite + Tailwind CSS
- Backend: Node.js + Express
- Database: Supabase Postgres
- Authentication: Supabase Auth with an HTTP-only session cookie issued by the backend
- Image storage: Supabase Storage or equivalent authenticated storage
- Notifications: in-app, optional email
- Scheduler: idempotent backend interval worker for reminder and overdue escalation jobs
- QR support: QR generation and browser scanning with manual fallback

## Environment requirements
- Node.js 22+
- npm 9+
- Supabase project with Postgres, Auth, and Storage enabled
- HTTPS-enabled deployment environment
- Supabase Auth email confirmation configured
- Access to an always-on backend process for reminder and expiry jobs

## Operational constraints
- Only authorized staff can create and manage institutional resources
- Students cannot register, list, or sell personal items
- All permission decisions must be enforced on the server
- No automatic penalty or fault assignment from an incident alone
- Self-registration is restricted to student accounts only
- Staff/admin roles must only be assigned by administrators
- The Supabase service-role key must remain server-side and must not be exposed in frontend environment variables

## Success criteria
- A judge can complete a resource request lifecycle without manual database changes
- Every approval/rejection/waitlist decision shows a clear reason
- Overlapping confirmed bookings are impossible
- Handover, return, and condition records remain traceable and reviewable
- Utilization and demand reports are generated from actual activity data

## Notes
- This is a single-college prototype and does not include multi-college support.
- Online payment, AI advice, and advanced institutional extensions are out of scope for the mandatory MVP.
